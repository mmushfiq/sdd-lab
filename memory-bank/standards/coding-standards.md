# Coding Standards

## Overview
Code style and quality standards for this project. Keep the build lean (no extra formatter or linter plugins), organize code by feature, and prove every story's acceptance criteria with tests against the real Spring context.

## Code Formatting

**Tool**: IntelliJ IDEA default Java code style
**Key Settings**:
- Indentation: 4 spaces
- Line length: 120 characters

**Enforcement**: In the IDE (reformat on save / before commit). Not enforced in the build.

## Linting

**Tool**: Java compiler warnings + IntelliJ inspections
**Base Config**: IDE defaults
**Strictness**: Balanced

**Key Rules**:
- No new compiler warnings - keep the build output clean
- No unused imports, fields or methods - dead code hides intent

## Naming Conventions

| Element | Convention | Example |
|---------|------------|---------|
| Packages | lowercase, by feature | `ch.martinelli.edu.hrs.reservation` |
| Views | `{Name}View` | `ReservationView` |
| Services | `{Name}Service` | `ReservationService` |
| Value objects / DTOs | Java `record` | `RoomAvailability` |
| Constants | `UPPER_SNAKE_CASE` | `MAX_GUESTS` |
| Flyway migrations | `V{n}__{snake_description}.sql` | `V1__create_room.sql` |

**File Naming**:
- Classes: one top-level type per file, file named after the type
- UI unit tests: `{Class}Test`, extends `HrsBrowserlessTest`
- Browser tests: `{Class}IT`, extends `PlaywrightIT`

## File Organization

**Pattern**: Feature-based packages

**Structure**:
```text
src/main/java/ch/martinelli/edu/hrs/
├── HrsApplication.java
├── core/                 # shared code (layouts, UI helpers, common utilities)
│   └── ui/
└── {feature}/            # e.g. reservation, room, guest
    ├── {Feature}View.java
    ├── {Feature}Service.java
    └── {Record}.java
src/main/resources/db/migration/   # Flyway V*.sql scripts
src/test/java/ch/martinelli/edu/hrs/  # mirrors main packages
```

**Conventions**:

- Tests: same package as the class under test, under `src/test/java`
- Generated jOOQ code: never edited by hand; regenerated by `./mvnw compile`
- Views call services; services run jOOQ queries. Views never use `DSLContext` directly.

## Testing Strategy

**Framework**: JUnit 6 with Spring Boot Test
**Coverage Target**: No fixed percentage - every acceptance criterion of a story has at least one test

**Test Types**:

| Type | Tool | When to Use |
|------|------|-------------|
| UI unit / use case | Vaadin Browserless (`HrsBrowserlessTest`) | Default for every view: exercise the use case through the UI against real services and H2 |
| Service integration | Spring Boot Test + jOOQ | Business rules with logic beyond what view tests cover |
| End-to-end | Playwright + Mopo (`PlaywrightIT`) | A few key flows only, e.g. complete booking |

**Conventions**:

- Test naming: method names describe behavior, e.g. `rejectsOverlappingReservation()`
- Test structure: Arrange-Act-Assert
- Mock strategy: no mocks for own code; use the real Spring context and H2 database. Test data comes from Flyway migrations or is created in the test.
- Commands: `./mvnw test` (unit), `./mvnw verify` (unit + integration)

## Error Handling

**Pattern**: Throw unchecked exceptions from services for business rule violations

**Custom Errors**: Yes - one runtime exception per meaningful rule where the UI must react, e.g. `RoomNotAvailableException extends RuntimeException`

**UI Errors**: Views catch business exceptions and show a Vaadin `Notification`. Field input is validated with Vaadin `Binder` before calling a service.

## Logging

**Tool**: SLF4J (Spring Boot default with Logback)

- `info`: business events (reservation created, cancelled)
- `warn` / `error`: failures and unexpected states
- Never log personal guest data (names, emails, phone numbers, payment details)
