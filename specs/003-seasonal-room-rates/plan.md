## Summary

Change of feature 001 (FR-001, FR-009, US1/AC5, US6/AC1, US7/AC1): the Manager maintains named seasonal rates
per room type (start date, end date, nightly rate, no overlaps); every other night costs the room type's
standard nightly rate. Each reservation stores the rate of each night in a new `reservation_night` table, so its
total, its price per night and monthly revenue are sums of frozen night rates (research R1, R7). One method
`AvailabilityService.nightRates` prices a stay for search, booking and change (R3); a change keeps the saved rate
of nights the reservation already had (R4). Existing reservations are copied to night rows at their old rate by
a migration; `reservation.nightly_rate` is dropped in a second migration once no code uses it (R2).

## Technical Context

**Language/Version**: Java 25

**Primary Dependencies**: Spring Boot 4.1.1, Vaadin Flow 25.3.1, jOOQ, Flyway (no new dependency)

**Storage**: H2 (file database in dev, in-memory in tests); new tables `seasonal_rate`, `reservation_night`
(V5); column `reservation.nightly_rate` dropped (V6)

**Testing**: JUnit with Spring Boot test, Vaadin Browserless (`HrsBrowserlessTest`), Playwright + Mopo
(`PlaywrightIT`), a Flyway migration test like `CancellationRuleMigrationTest`

**Target Platform**: Server-side Vaadin web app, desktop and tablet browsers

**Project Type**: Web application (single Maven module, server-side UI)

**Performance Goals**: None new; ten rooms, at most 30 nights per stay. Search reads the seasonal rates of the
stay once, not per room or night.

**Constraints**: Existing reservations keep their prices (FR-008); saved night rates never change through rate
maintenance (FR-006); overlapping seasonal rates of one room type are impossible, also when two Managers save at
the same time.

**Scale/Scope**: 2 migrations, 1 new view with 1 new service, 1 new value type, 4 views and 3 services changed,
~12 test classes changed or added.
